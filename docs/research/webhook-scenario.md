# Сценарий изменения сервиса доставки webhook

Подготовлен 21 ноября 2026. taskId webhook-retry-v1. Это кандидат для следующего
диагностического эксперимента на более сложной задаче. Новых модельных прогонов
по нему ещё нет. Усложнение само по себе не гарантирует преимущества MetaACO.

## Пользовательская задача

В существующий небольшой CommonJS сервис добавить подписки и приём событий,
идемпотентную постановку на доставку, fan-out по подписчикам, HMAC-подпись и
доставку с повторами. Сохранить health endpoint и версию API.
Состояние находится в памяти одного процесса. Sender и clock внедряются, что
позволяет детерминированно проверить время и сбои без внешней сети.

Изначально работают GET /health, version() и ответ 404 для неизвестного маршрута.
Новые функции представлены заглушками с фиксированными интерфейсами. Получается
контролируемое изменение минимального MVP, а не разработка произвольного сервиса
с нуля. Транспортный адаптер принимает объект запроса и возвращает ответ. Настоящий
TCP/HTTP сервер, durable storage, восстановление после crash, БД, распределённые
воркеры и реальные сетевые вызовы в этот сценарий не входят.

| Модуль | Работа |
|---|---|
| app.cjs | Подписки, приём событий, получение статуса, валидация и коды ответа |
| store.cjs | Изолированное состояние, идемпотентность, атомарный claim и settle |
| worker.cjs | Асинхронная отправка, обработка исключений, повторные попытки |
| signature.cjs | HMAC-SHA256 точных отправляемых байтов |

Полные требования, интерфейсы и исходники находятся в
[task.js](../../examples/webhook-scenario/task.js). Формирование запроса и
закреплённого TestSpec — в [index.js](../../examples/webhook-scenario/index.js).
Все методы получают одинаковое описание и публичные контракты.

## Почему здесь возникает выбор организации работы

Один агент может изменить все четыре файла. Три агента могут независимо писать
хранилище, API и доставку с подписью по общим контрактам. Интеграция затем должна
собрать согласованный снимок. Цена параллельности включает дополнительные вызовы,
передачу артефактов и риск нарушения контрактов. Один запрос Flash или Pro остаётся
полноценным конкурентом, а не намеренно ослабленным baseline.

Опциональные analyze/design/review имеют skip или две модели. Модели реализации
и рефакторинга выбираются отдельно по этапам. При трёх компонентах целевой каталог
при сохранении текущих правил декодера имел бы 3³·2·(10+48)=3132 маршрута.
Это расчёт пространства для будущей конфигурации, не число выполненных запусков.
Полный платный перебор не является условием подготовки или обучения.

Роли и владение файлами включены в scenario payload. Store владеет store.cjs,
API — app.cjs, delivery — worker.cjs и signature.cjs. Компонентные агенты получают
общие требования и контракты, затем явное ограничение своих файлов. Полный снимок
возвращают monolithic implement, integrate и refactor. Не добавлять противоречивое
требование полного снимка в задания отдельных компонентов. Совпадение заявок на
файл остаётся ошибкой, которую должен обнаруживать исполнитель.

## Независимая приёмка

Подготовлены 12 именованных target tests.

1. Валидация подписок и повторного ID.
2. Валидация события и case-insensitive ключ идемпотентности.
3. Повторный запрос с переставленными вложенными JSON ключами без повторной доставки.
4. Конфликты ключа и ID события.
5. Fan-out и фиксация подписок на момент enqueue.
6. Отсутствие мутаций входа и утечки изменяемого состояния в ответ.
7. HMAC точных wire bytes, включая Unicode.
8. Успешная отправка с подписью только один раз.
9. Исключение sender, задержка повтора и внедрённые часы.
10. Исчерпание лимита после non-2xx.
11. Два конкурентных worker не отправляют одно задание одновременно.
12. Сбой одного получателя не блокирует другого.

Две regression проверки сохраняют version/health и 404. Тесты используют настоящие
assertions, crypto и Promise concurrency, не проверяют совпадение кода с эталоном.
Требуется только поведение на публичных контрактах. Нет зависимости от скорости
машины или произвольных sleep. Sender не обращается в сеть.

При офлайн-калибровке baseline прошёл регрессии; все 12 target tests упали по
ERR_ASSERTION в ожидаемых именах. Отдельный эталон прошёл GREEN и REFACTOR gates.
Это калибровка evaluator на известном корректном коде, не доказательство реального
TDD разработки моделью. Мутации эталона с двойным claim, неверной подписью и ранним
retry обнаружены assertions соответствующих тестов.

Эталон находится только в test/fixtures/webhook-reference.js. Он не включается
в baseSnapshot, task description, role prompts или учебный банк. Исходники тестов
хранятся в репозитории для аудита, однако модельный runtime должен передавать только
request.description и артефакты родителей. Изоляция production snapshot от control
tests проверяется существующим evaluator.

## Подготовка без API

Команда node examples/prepare-webhook-scenario.js печатает состав и хеши.
С --out /absolute/new-scenario.json создаётся JSON-файл эксклюзивно, без перезаписи.
Это описание сценария и TestSpec, а не уже готовый к /metaaco-skills job.
Фикстура поддерживает локальный независимый runner; платное исполнение должно
использовать закреплённый Docker-образ с теми же тестами.

## До реального экспериментального запуска

Нужно обобщить stock-специфический launcher под этот task и общие интерфейсы,
зафиксировать каталог моделей/навыков, ресурсы, прогнозы и протокол исследования.
Не подавать готовые 700 stock-наблюдений как подходящий опыт для этой новой задачи
только из-за совпадения ID навыков. Версии промптов и контракты должны входить
в provenance применимости истории. Frozen перенос потребует отдельной учебной
выборки и явно заданного правила переноса.

Текущий DeepSeek adapter ограничивает ответ 1024 токенами. Для четырёх исходных
файлов и JSON escaping этот предел нельзя считать достаточным. Перед запуском
нужны общий увеличенный лимит для direct и orchestration, учёт суммарных токенов
и корректные trusted quotes для нового лимита. Нельзя дать direct маленький
выходной бюджет, а нескольким агентам суммарно большой и объявить это выигрышем.
Проверить maxArtifactBytes/maxInputBytes на полном снимке и интеграции трёх выходов.
Прогнозы длительности остаются прогнозами, неизвестные измерения не заменяются нулём.

Следующий контрольный запуск должен проверить формат ответа, передачу файлов,
отсутствие конфликтов и неизменность acceptance tests. После него регистрируется
конечная матрица с direct Flash/Pro, informed Fixed и соответствующими алгоритмами
выбора. Primary — независимая корректность, TDD — отдельный показатель как в direct-v2,
все расходы и ошибки сохраняются. Повторы и модели сравниваются в общем временном
окне. Новая задача пока имеет статус validation-candidate, а не слепой held-out test,
поскольку авторы уже видели её эталон и тесты.

Для научного вывода нужны несколько независимых задач с разной структурой и уровнем
сложности, а также анализ локальной целевой функции на сохранённых данных. Если
прямой запрос снова окажется лучшим, этот результат сохраняется. Не повышать сложность
или менять критерии после просмотра исходов ради преимущества MetaACO.
