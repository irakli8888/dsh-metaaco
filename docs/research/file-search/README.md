# Поиск файлов с MetaACO

Офлайн-пилот от 23 ноября 2026 года. Файлы эксперимента находятся в ветке
`codex/file-search-experiment` на базе `dsh-metaaco@3a696b4`. Корпус зафиксирован
на `dsh-metaaco@85a501d` и `deepseek-harness@22ddee37`.

## Запуск

Нужны Git, Python 3.10+ и локальные копии с указанными Git-объектами. Из корня dsh-metaaco:

```sh
python3 -B python/file_search_benchmark.py compare \
  --harness /path/to/deepseek-harness --output /tmp/file-search
python3 -B python/file_search_benchmark.py search --revision 85a501d \
  --policy /tmp/file-search/policy.json \
  'Где проверяется расписание на превышение доступных ресурсов?'
```

`search` без `--policy` использует каскад B. `--repo` позволяет искать
в другом локальном Git-репозитории. Каждый запуск CLI загружает снимок в память.
В бенчмарке снимок живёт весь прогон. Результат содержит до пяти путей с номером
строки и фрагментом, трассу шагов и причину остановки.

## Варианты

- **A** — штатный агент Harness. В исходниках `22ddee37` вход для разового
  задания — `dsh --profile headless "<запрос>"`. Base bundle подключает
  `dsh-tool-fs-search` и `dsh-tool-fs`. Модель выбирает `glob` и `grep`
  (оба запускают ripgrep), `read` и другие доступные инструменты, затем формирует
  ответ. Штатный индекс символов и фиксированный каскад в этой цепочке не обнаружены.
  Установленный CLI сообщает `0.2.2-rc.3`. Модельный baseline в офлайн-пилоте
  недоступен без разрешённого бюджета, поэтому его метрики и токены записаны как `null`.
- **B** — локальный индекс токенов пути и построчного текста, включая
  декларации, распознанные по шаблону. Порядок `path → text → follow`.
  `follow` ищет декларации по термам запроса и именам вызовов из найденных
  фрагментов. Разбор лексический, с ограниченным русско-английским словарём.
- **C** — тот же снимок, индекс, инструменты, ранжирование и лимит в три шага.
  Политика задаёт приоритет действий для трёх состояний: начало, 1–5 совпавших
  файлов на предыдущем шаге, 0 или больше 5 файлов. Тип запроса определяется
  по форме текста: имя файла, идентификатор или описание. При 1–5 совпадениях
  политика также может остановить поиск.
- **D** — контроль индексации. Каскад B перебирает прямые таблицы токенов всех
  файлов в памяти вместо получения кандидатов из инвертированных списков.
  Скоринг, ранжирование и формат ответа те же. Контроль измеряет эффект
  инвертированных списков при уже токенизированном корпусе.

C переиспользует `search_decisions` и поставляемый многоколониальный MetaACO.
Первая альтернатива каждой группы в перестановке определяет, какое действие
попробовать первым в конкретном состоянии. Оценка политики по tuning-запросам
лексикографически минимизирует промахи в топ‑5, затем промахи на первом месте,
затем число шагов. Алгоритм сохраняет UCB, репликацию, архив, мутации параметров
и локальный поиск. Бюджет — 60 оценок для каждого типа и seed. Политика фиксируется
до итогового прогона. При запросе выполняется её выбор следующего шага по состоянию,
а затраты самого solver записаны отдельно в `training`. LRU кэш на 2048 шагов
привязан к снимку, используется при оценке повторных маршрутов и сбрасывается
при обновлении индекса.

## Протокол

[Разметка](queries.tsv) содержит 32 запроса, 12 для настройки и 20 для оценки.
Запросы о вызовах размечены по файлу реализации. Оба репозитория представлены
в обеих частях, разные задания могут ссылаться на один файл.
Эталонные пути передаются только оценщику выдачи. Тестовая серия повторена три раза
с парными запросами и перемешанным порядком локальных режимов. Каждый повтор C
использует свой seed обучения. Кэш очищается перед каждым замером. Время полной
выдачи включает выбор маршрута, поиск, ранжирование и сериализацию ответа.
Построение индекса учитывается отдельно. Корпус содержит UTF‑8 файлы до 128 КиБ из
`git archive`, включая скрытые файлы и исключая двоичные файлы и симлинки.
Время обновления — замер пересчёта одного небольшого файла с последующим
восстановлением исходного снимка. Модельные вызовы, токены и переданные модели
байты для B/C/D равны нулю.

[Результаты по попыткам](results.jsonl) содержат совпадения, время каждого шага,
выдачу, итоговый ранг и причину остановки. В [сводке](summary.json) сохранены SHA-256
входов и кода, версии среды, результаты по типам и стоимость обучения. Файл
[policy.json](policy.json) содержит замороженную политику seed 42 для команды поиска.

## Результат

| Вариант | Hit@1 | Hit@5 | Медиана, мс | p95, мс | Шагов в среднем |
| --- | ---: | ---: | ---: | ---: | ---: |
| A. Штатный Harness | — | — | — | — | — |
| B. Индекс и фиксированный каскад | 70,0% | 80,0% | 0,893 | 101,76 | 3,00 |
| C. Индекс и MetaACO | 73,3% | 78,3% | 0,906 | 93,05 | 2,77 |
| D. Фиксированный каскад с перебором | 70,0% | 80,0% | 1,209 | 126,04 | 3,00 |

**Индекс ускорил фиксированный каскад.** Медиана B на 26% ниже D, p95 на 19%
ниже. В 60 парных запусках B и D совпали все ранги, пути и фрагменты.
Для 169 файлов dsh-metaaco чтение корпуса заняло 25,8 мс, сборка индекса
147,0 мс, обновление одного файла 0,21 мс. Для 19 051 файла Harness — 631,3 мс,
17,82 с и 0,17 мс соответственно. Повторная сборка при каждом вызове CLI
перекрывает выигрыш поиска. Для таких задержек нужен уже загруженный индекс.

**Дополнительный выигрыш MetaACO при сохранении Hit@5 не подтверждён.** C снизил
p95 на 8,6% и делал меньше шагов, но медиана выросла на 1,5%, а Hit@5 снизился на
один результат из 60. При приоритете Hit@5 и медианы на этом наборе предпочтителен
фиксированный каскад B. Обучение политики заняло 456, 16 и 19 мс на трёх seeds
последовательно с общим кэшем. Пилот измеряет итоговую политику целиком.
Сравнение с другими способами обучения той же политики потребует отдельной серии.

| Тип запроса | Запросов | B Hit@1 / Hit@5 | C Hit@1 / Hit@5 | Медиана B → C, мс |
| --- | ---: | ---: | ---: | ---: |
| Имя файла | 5 | 100 / 100% | 100 / 100% | 0,967 → 0,986 |
| Символ | 4 | 100 / 100% | 100 / 100% | 21,67 → 21,33 |
| Конфигурация | 3 | 0 / 0% | 0 / 0% | 1,038 → 0,672 |
| Описание логики | 4 | 50 / 100% | 66,7 / 91,7% | 0,570 → 0,090 |
| От вызова к реализации | 4 | 75 / 75% | 75 / 75% | 21,73 → 21,83 |

- **Ускорение, №21.** По описанию оценки LinUCB C остановился на `path` и
  поставил реализацию первой. B после текстового поиска поднял документацию над
  реализацией. Медиана 0,357 → 0,033 мс, ранг 3 → 1.
- **Потеря качества, №20.** По вопросу о превышении доступных ресурсов B во всех
  повторах поставил `python/vendor/rcpsp/core.py` первым. C начинал с `follow`;
  seed 42 затем выбрал `text` раньше `path`, и реализация выпала из топ‑5.
  Остальные два seed вернули её первой, остановившись после `follow → path`.
- **Замедление, №30.** По описанию выборки `glob` C менял порядок всех трёх
  шагов. Первое место осталось прежним, медиана выросла с 47,91 до 52,11 мс.
- **Тот же маршрут, №23.** По `advanceFeedback` обе версии прошли
  `path → text → follow` и поставили файл реализации первым.

Повторы дают 60 замеров на вариант, но независимых заданий всего 20.
Небольшая выборка, два репозитория и лексическое ранжирование ограничивают
обобщение. Особенно заметна слабая выдача по описаниям конфигурации.
Числа показывают задержку внутри процесса по загруженному снимку и не включают
сетевые запросы или задержку запуска CLI.
