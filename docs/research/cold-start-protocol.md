# Протокол обучения с пустым банком

Версия stock-cold-start-pilot-v1, 20 ноября 2026. Статус — проект протокола и
офлайн-проверка закреплённой конфигурации. Исполнитель online-серии ещё требует
доработки. Настоящий протокол не был зарегистрирован до предыдущих экспериментов.
Авторы уже видели результаты полного перебора, поэтому повтор на этой задаче
имеет статус исследовательского пилота. Подтверждающая серия требует новых задач.

## Исследовательский вопрос

Способна ли система, начиная с пустой истории, находить подходящие маршруты
при ограниченном числе реальных исполнений? Дают ли MetaACO и накопленные
наблюдения преимущество относительно простых способов выбора? Проверяется
адаптация оркестратора. Веса DeepSeek не изменяются.

Основная единица повторения — независимая история метода при заданном seed.
Все методы получают одинаковую задачу, каталог, модели, тесты и лимиты.
У каждого метода и seed свой пустой банк. История других методов, seeds,
предыдущих серий и полный перебор в селектор не поступают.

## Матрица пилота

| Параметр | Значение |
|---|---|
| Задача | stock-reservation из templateStudyTasks, исходный base-v1 |
| Статус задачи | train, validation/test в этом пилоте пусты |
| Методы | Все семь режимов из EXPERIMENT_MODES |
| Seeds | 7, 11, 19, 23, 31 |
| Число попыток на method/seed | 20 |
| Общий максимум | 700 попыток, 35 раздельных банков |
| Модели | Flash и Pro, одинаковый закреплённый тариф для всех режимов |
| Маршруты | 1836 из исправленного каталога с раздельными компонентными промптами |
| Поиск MetaACO | Три начальные колонии, максимум 100 оценок на выбор |
| Параллельность | Одна попытка всей серии одновременно, два agentSlots в её DAG |
| Deadline | 120 секунд на попытку |
| Docker | sha256:116b800c3754b440ee0aa3ed2f20f5bf3d99a554bfd9adeea09ea8017f6e85f5 |
| Остановка при первом успехе | Нет, измеряется последующее поведение |
| Автоматический retry | Нет, каждый вызов и попытка учитываются отдельно |

Двадцать попыток и пять seeds выбраны как конечный диагностический пилот.
Статистическая мощность такого размера не обоснована. Семьсот попыток — максимум,
а не количество запросов. Каждый маршрут вызывает несколько моделей. Денежная
стоимость и максимальное число вызовов вычисляются по финальному manifest до старта.
Историческое разрешение расходов владельца не является числовым лимитом manifest.

## Определения baseline для совместного пространства навыков

| Метод | Правило выбора и допустимая история |
|---|---|
| Random | Равномерный выбор уникального маршрута из каталога с повторениями по seed; без истории |
| Fixed workflow | implement Flash → refactor Flash, один и тот же маршрут все 20 раз |
| Cheapest | Минимальная заранее вычисленная цена маршрута по общему прогнозу токенов и тарифу; равенство разрешается каноническим ключом |
| Historical best | Маршрут с лучшим средним reward в собственном банке; при отсутствии истории канонический выбор |
| Contextual bandit | Disjoint LinUCB по маршрутам-рукам на признаках задачи и собственных исходах; без MetaACO |
| MetaACO without bank | Настоящий skill-поиск с теми же исходными прогнозами, без исторических quality evidence |
| MetaACO with bank | Тот же solver с собственными уже завершёнными исходами и явно закреплённой политикой исследования |

Для fixed принят короткий маршрут из структуры задачи. Его успешность уже известна
авторам по прошлой серии, поэтому пилот не может рассматриваться как слепой тест.
Cheapest выбирает по прогнозам, не получает реальные затраты из полного перебора.
Методы без истории продолжают журналировать свои исходы для итогового анализа.
Элитный архив, репликация и локальный поиск одинаково включены в обоих MetaACO.

Начальные прогнозы задаются до серии из общих технических параметров и не
подгоняются по E1/E2/E3/E4. Параметры LinUCB, reward, разрешение равенств,
seed derivation на каждый выбор и token forecasts закрепляются в исполняемом
manifest. Пока эти численные параметры не закреплены, серия не готова к старту.

У MetaACO with bank политика исследования требует отдельного решения до запуска.
Текущий least-observed после поиска исследует кандидаты и не обеспечивает
постепенного перехода к эксплуатации. Его следует сравнивать как явно названную
политику. Изменение правила после просмотра результатов требует новой версии
протокола. Прогнозы времени и цены в основном сравнении фиксируются для всех
методов, чтобы эффект качества не смешивался с калибровкой прогнозов. Обучение
прогнозов времени выделяется в последующую ablation.

## Цикл попыток

1. Создать чистый банк method/seed и записать его стартовый пустой снимок.
2. До dispatch сохранить решение, snapshot ID, число доступных прошлых исходов,
   solver seed, трассу кандидатов и расходы самого выбора.
3. Выбрать маршрут и исполнить его с исходного base-v1, не с кода предыдущей попытки.
4. Запустить baseline, ожидаемый RED, GREEN и REFACTOR через закреплённый evaluator.
5. Сохранить все исходы, артефакты, тесты, токены и стоимость. Завершить попытку
   перед созданием следующей версии истории.
6. Обновить только собственную online-train историю. Текущая или будущая попытка
   не может участвовать в выборе самой себя.
7. Выполнить следующий round для всех method/seed, затем переходить к новому round.

Внутри round порядок method/seed детерминированно перемешивается закреплённым seed,
чтобы методы не выполнялись большими блоками в разное время. Последовательный запуск
уменьшает конкуренцию за ресурсы. LLM sampling недетерминирован, парные solver seeds
не означают одинаковые случайные ответы модели.

## Исходы и ошибки

Сохраняются success, failed, timeout, cancelled, interrupted, inconclusive и причины.
Исполнение, не дошедшее до проверки, не считается успешным и расходует слот попытки.
Для основного бинарного показателя успех определяется приёмкой. В модели качества
следует закрепить, какие технические ошибки получают отрицательную награду, а какие
исключаются. Текущий LinUCB и routeQualityEvidence трактуют такие ошибки по-разному.
До запуска требуется единая спецификация либо явно названные отличающиеся политики.

Ошибки API 401/403, недостаток средств, недоступность evaluator, повреждение банка
или нарушение целостности данных останавливают весь запуск до диагностики.
Остановку и незавершённые попытки журналируют. Не запускать автоматические платные
повторы. После перезапуска владелец процесса и состояние банка должны быть однозначны.
Проблему конкретного сгенерированного кода фиксируют как исход маршрута.
Изменение промптов, тестов, моделей или тарифов внутри серии запрещается протоколом.
При необходимости изменения фиксируется окончание текущей версии серии.

## Метрики и анализ

Основной показатель пилота — число реальных попыток до первого успеха, ограниченное
20 попытками. Если успеха нет, наблюдение считается цензурированным на 20, а не
выдуманным успехом на 21-й попытке. Дополнительно сохраняются число successes из 20,
суммарное время и стоимость до первого успеха и по всей траектории, число вызовов,
уникальные маршруты, повторные посещения и причины остановки.

Для итогового отчёта показывать learning curves по round с результатами каждой
из пяти историй, долю решённых ячеек к попыткам 1/5/10/20, все затраты и missingness.
Разница между методами оценивается по парным seed-повторам только для этой задачи.
Она не обосновывает выводы о всём классе программирования. Медианы успешных
попыток дополнительно маркируются как условные на успехе. Неизвестная полная цена
остаётся null, известные расходы показываются нижней границей отдельно.

E1/E2 используются после серии только для сравнения найденных маршрутов с
наблюдаемым эталоном. Они не доступны селекторам и не задают прогнозы или reward.
Не требуется точное совпадение route ID с лидером одноразового перебора. Важны
новые независимые результаты приёмки, измеренное время и расчётная стоимость.

## Готовность исполнителя и офлайн-проверка

Команда node examples/cold-start-protocol.js печатает закреплённую конфигурацию,
хеш, 35 банков и максимум 700 попыток без чтения секретов, запросов к API или записи
банка. validateColdStartProtocol проверяет равенство дизайну v1, уникальность seeds
и разделение ID. Изменение условий требует новой версии. Это проверка конфигурации,
она не подтверждает отсутствие утечек в ещё не реализованном online-исполнителе.

Существующий experiments runner предназначен для frozen held-out режима и выбора
готовых arms. Его MetaACO режимы планируют DAG, а данная серия требует совместного
поиска навыков и моделей с online history. Использовать их как взаимозаменяемые
режимы без адаптации нельзя. До реального исполнения необходимы следующие работы.

- Один источник исправленного каталога для всех семи методов с хешами промптов и тестов.
- Отдельный online runner с собственной историей method/seed, очисткой старта и
  тестами против доступа к E1/E2 и чужим банкам.
- Явный research-mode для прошлых попыток той же train-задачи без изменения held-out
  правил публичного runSkillAttempt.
- Закреплённые параметры baseline, reward и исследования MetaACO, одинаковый admission.
- Пилот с synthetic исходами и управляемыми авариями, проверка sequential ordering,
  сохранения terminal попыток и пустых снимков в каждом из 35 банков.
- Manifest commit/source hashes, модели, тарифы, image, runtime versions и конечные
  правила расходов. Полный денежный предел должен иметь явное значение или null.

## Переход к проверке переноса

После анализа пилота выбрать новые семейства задач, которых не было в предыдущих
сериях. Сначала закрепить acceptance tests, train/validation/test, задачи и размеры
повторов. Подбор гиперпараметров идёт по train/validation. В test история заморожена.
Повторы stock-reservation служат диагностикой same-task адаптации и не входят в
доказательство переносимости. Протокол подтверждающей серии оформляется отдельно
до её запуска с primary endpoints и обоснованием объёма выборки.
