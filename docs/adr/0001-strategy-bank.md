# ADR 0001: локальный Strategy Bank

Принято после согласования архитектуры 25 октября 2026 года.

## Решение

Первый этап — самостоятельный persistence API `dsh-metaaco/bank`, без изменения Harness runtime или MetaACO. Используется встроенный `node:sqlite` (DatabaseSync), доступный на минимальной версии Node проекта, без стороннего драйвера и изменения lockfile. Синхронный интерфейс подходит для небольших локальных историй; длительные выгрузки и большой поток событий впоследствии можно вынести в worker без изменения контрактов хранения.

SQLite использует foreign keys, STRICT tables, транзакции BEGIN IMMEDIATE для записи, synchronous=FULL и busy_timeout=5000. Выбран стандартный rollback journal: WAL для первоначальной нагрузки не требуется. Несколько процессов могут читать/писать одну локальную БД, записи сериализуются. После пяти секунд блокировки вызывающий получает ошибку; скрытых retry и повторных внешних действий нет. Сетевые файловые системы и распределённые писатели не поддерживаются.

Миграции в src/bank/migrations.js применяются вместе с PRAGMA user_version в одной транзакции. Более новая версия БД отклоняется. Начальная миграция создаёт стратегии, неизменяемые TaskRequest, попытки, события и связи артефактов. Форматы model usage/test reports пока хранятся как payload событий; их типизация и автоматический сбор относятся к следующим этапам.

## Идентичность и состояния

Версия стратегии — пара (strategyId, version). Повтор идентичного register идемпотентен, изменение содержимого требует новой версии. TaskRequest закрепляется по taskId; новая исходная ревизия или TestSpec требуют нового taskId. Каждая попытка получает отдельный caller-supplied attemptId; beginAttempt не перезаписывает существующие попытки.

Состояния: running → succeeded / failed / inconclusive / cancelled / interrupted. Обратные переходы и изменение terminal outcome запрещены. Повтор finalize с теми же данными допустим. Поздний billing и исправления outcome пока не поддерживаются: они требуют отдельного версионированного протокола этапа метрик; нельзя незаметно переписать завершённую попытку.

События имеют составную уникальность (attemptId,eventId) и возрастающий sequence внутри попытки. Retry с тем же каноническим JSON возвращает исходное событие; конфликт отклоняется. Идемпотентные повторы уже существующих событий и связей артефактов допустимы даже после terminal state; новые записи после завершения отклоняются.

Открытие базы никогда не меняет running. recoverInterrupted требует явного списка IDs и причины. Владелец должен убедиться, что соответствующие исполнители остановлены. Это устраняет ошибку, когда второй живой процесс открывает БД и считает чужую работу прерванной. Автоматического resume и API-вызовов нет.

## Артефакты и экспорт

Байты живут вне SQLite под именем SHA-256. Временный файл полностью записывается и fsync-ится, затем публикуется hard link без перезаписи существующего содержимого; каталог fsync-ится до записи ссылки в БД. Чтение и повторная запись проверяют длину и digest. Внешнее изменение файла обнаруживается как integrity error. Поддерживаются локальные файловые системы с hard links и fsync каталога.

При crash между публикацией и записью БД возможен файл без ссылки или .tmp-файл, но не успешная запись ссылки на частично записанные байты. Сборщик мусора не входит в первый этап и не удаляет файлы автоматически. Хранилище рассчитано на доверенного локального владельца; это не защита от пользователя, способного менять саму БД.

exportJsonl возвращает metadata в стабильном порядке из одной read transaction. Результат идентичен при неизменной БД и пригоден для сравнения/анализа. Это не обещание идентичных timestamps независимых запусков. Для резервной копии нужны и JSONL, и каталог artifacts; автоматический импорт/восстановление из JSONL пока отсутствует. Данные по умолчанию никуда не отправляются.

## Граница доверия

Bank хранит EvaluationResult вызывающего кода и структурно запрещает success с пустым/проваленным/пропущенным обязательным набором. Он не запускает тесты и не подтверждает истинность отчёта. Полный gate по immutable TestSpec и доказательствам TDD будет реализован evaluator на этапе 2. Завершение Harness само по себе записывается как inconclusive, если независимой оценки нет.

Измеренные и прогнозные поля outcome хранятся раздельно; Bank не создаёт метрики, не рассчитывает тарифы и не подставляет нули вместо null. JSON проверяется на потери данных, циклы, undefined, non-finite numbers и exotic objects. JSON Schema описывает storage inputs; JS дополнительно проверяет уникальность child/test IDs и lifecycle. Оpaque JSON payload/testSpec/provenance будут расширены версиями следующих компонентов.

## Проверка

TDD RED: тестовый файл создан до реализации; запуск упал с ERR_MODULE_NOT_FOUND для нового Bank. GREEN: тесты проверяют сохранность после reopening, потерю владельца в отдельном процессе с exit(23), запрет ложного success по структурным данным, конфликты версий, rollback, отмену, integrity артефактов и повтор событий. Три независимых процесса одновременно добавляют 45 собственных и одно общее событие: ровно 46 записей, непрерывный sequence, без двойного usage. Существующие Harness-тесты сохраняются.
