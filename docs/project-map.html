Зачем всё это

Пять принципов, из которых собран проект

Если запомнить только этот блок — уже будет понятно, почему компонентов так много.

01

Сначала доказательство, потом оптимизация

Банк, evaluator и метрики появились раньше селектора и ACO. Оптимизатор без проверенных исходов учился бы на самоотчётах агента.

02

Планировщик не исполняет

Python-MetaACO решает, что и в каком порядке запускать. Harness исполняет узлы и передаёт артефакты. Это разные ответственности и разные языки.

03

Две неопределённости — два алгоритма

LinUCB выбирает стратегию и маршрут моделей по контексту. UCB внутри MetaACO решает, какой колонии дать бюджет. Это не один и тот же «UCB».

04

Память отдельно от текущего поиска

Strategy Bank — постоянная история задач и попыток. EliteArchive — временная полка лучших расписаний внутри solver. Их нельзя путать.

05

Деньги — с гарантией, неизвестное — null

Перед вызовом модели нужен верхний предел стоимости и резерв в ledger. Расчёт по тарифу не выдаётся за счёт провайдера, а неизвестный usage не считается нулём.

Главная идея за 20 секунд

Это не «умный промпт». Это фабрика проверенных решений: она фиксирует критерии до работы, планирует граф под ограничения, исполняет его по частям, независимо проверяет и только затем превращает исход в обучающий сигнал.

ШАГ 01 · ДО ИСПОЛНЕНИЯ

Зафиксировать задачу и проверку

Пока ничего не сгенерировано, но уже известно, что будет считаться успехом.

  • TaskRequest: taskId, репозиторий и baseCommit, требования, acceptance criteria.
  • TestSpec: наборы тестов, закреплённые команды и expectedRedTests. Спека и её хеш фиксируются до патча.
  • baseSnapshot {revision, files} обязан совпадать с baseCommit; подменить контрольные тесты файлами от агента нельзя.
  • UserPolicy: разрешённые модели и инструменты, лимиты денег и времени, concurrency, минимальное качество, веса целей.
  • Задача заранее отнесена к train / validation / test. Признаки для истории и для нового запроса считаются одинаково.

Артефакт шага

pinned request + test spec + policy + base snapshot

Не путать

«Модель сказала, что всё готово» — не критерий. Без закреплённых тестов успех не измерим.

ШАГ 02 · КЛАССИФИКАЦИЯ

Понять задачу, не заглядывая в ответ

Контекст нужен, чтобы сравнивать похожие задачи и выбирать маршрут по признакам, известным заранее.

  • Правила rules-v1 определяют тип: bugfix, feature, refactor, testing, documentation или unknown.
  • Стек: python, javascript, typescript, java, rust, go, react, node, sqlite, postgres. Неизвестный стек получает отдельный признак.
  • Вектор selector-context-v1 — 18 чисел: intercept + 6 типов + 10 стеков + unknown-stack.
  • Одинаковые правила применяются к прошлым попыткам и к новой задаче; иначе сравнение смещено в пользу одного из маршрутов.
  • Сложность и произвольные требования пока в вектор не входят — это заявленное ограничение, а не забытая деталь.

Артефакт шага

task-analysis с типом, стеком и 18-мерным контекстом

Не путать

Исход попытки не может быть признаком: это утечка из будущего. Анализ выполняется до первого агента.

ШАГ 03 · ДОПУСК И ВЫБОР

Отфильтровать кандидатов, затем учиться

Сначала политика, только потом LinUCB: исследовательский бонус не обходит запреты.

  • Кандидат = стратегия + маршрут моделей/инструментов + прогнозы времени, денег и качества + признак TDD.
  • Отбрасываются запрещённые модели и инструменты, лишняя concurrency, несовместимый тип задачи и нарушение лимитов.
  • Arm — это SHA-256 от стратегии и маршрута. Смена версии, модели, инструментов или concurrency создаёт новый arm; прогнозы arm не меняют.
  • Disjoint LinUCB: своя ridge-модель на arm, score = xᵀA⁻¹b + α·√(xᵀA⁻¹x).
  • Награда: подтверждённый success ≥ 0; failed/timeout/cancelled/interrupted −1; inconclusive — null, модель не обучается.
  • Снимок истории замораживается по train-списку и cutoff. На отложенном тесте используется frozen-снимок.

Артефакт шага

SelectionDecision: выбранный arm, полная policy, причины исключения кандидатов

Не путать

Прогноз — не гарантия и не верхняя граница стоимости. Selector не резервирует деньги и не запускает модель.

ШАГ 04 · ПЛАНИРОВАНИЕ

Спланировать граф: MetaACO

Настоящий Python-решатель переставляет альтернативы и декодирует их в допустимый DAG с приоритетами.

  • Модель — RCPSP: работы = шаги, длительности = прогнозы в секундах, ресурсы = слоты агентов, зависимости = DAG.
  • Группы решений: обязательные implement и refactor; опциональные analyze, design, write-tests, review или skip; layout monolith / components; маршрут модели для каждого навыка.
  • Муравей строит перестановку альтернатив. Декодер берёт первую встреченную альтернативу каждой группы — получаются навыки, модели и структура графа.
  • Феромон — матрица «позиция × работа». Испарение и отложение идут в собственной матрице выбранной колонии.
  • Из выбора строится DAG: зависимости фиксированы правилами, а перестановка задаёт приоритеты готовых узлов. Порядок — не запрет параллельности.
  • Бюджет — жёсткий фильтр: вариант дороже лимита отбрасывается до исполнения. Стоимость не «компенсируется» скоростью.
  • SSGS (последовательная схема) ставит работы по одной на самое раннее допустимое время; Cmax — прогнозная длительность в секундах.
  • UCB между колониями: сначала неисследованные, затем mean + c·√(log T / mass). Награда — относительное улучшение. Колонии не работают параллельно: UCB выбирает одну на итерацию.
  • Элитный архив усиливает феромоны, репликация с мутацией создаёт новую колонию, локальный поиск меняет места в порядке.
  • Цель совместного поиска: сначала сглаженная успешность маршрута из банка, затем более короткий makespan. Неизвестный маршрут получает нейтральный приоритет.

Артефакт шага

plan v3 + trace оценок (до 100) + выбранные маршруты и приоритеты

Не путать

Cmax — прогноз, а не фактическая latency. Совпадение с перебором на одном графе не гарантирует оптимум на других.

Где смотреть

ШАГ 05 · ИСПОЛНЕНИЕ

Исполнить граф с бюджетом

Исполнитель не решает, что делать. Он выполняет уже проверенный план и передаёт артефакты.

  • Узел: id, prompt, dependsOn, inputs, slots, model. Зависимость без input означает только порядок, а не передачу результата.
  • Готовые узлы запускаются, если их slots помещаются в ёмкость. Барьеров нет: независимые ветки перекрываются во времени.
  • Каждый узел — отдельный Harness run. Выход — текстовый артефакт по SHA-256; потомок получает только явно указанные inputs.
  • Budget adapter: проверка route/consent → quote верхнего предела → резерв в SQLite ledger → dispatch. Параллельные вызовы не тратят один остаток.
  • К моменту создания runtime baseline и ожидаемый RED уже пройдены; иначе агенты не вызываются.
  • Cancel и timeout прекращают новый dispatch, отменяют активные runs и ждут освобождения handles; dispose() обязателен.
  • Автоматического retry/resume нет: после сбоя создаётся новая попытка решением оркестратора.

Артефакт шага

execution report, artifacts dag-output/<id>, события dag-start/task/finish

Не путать

Слоты логические, не CPU/RAM. Исполнитель не финализирует попытку и не считает деньги.

Где смотреть

dag-executor.md · adaptive-attempt.md

ШАГ 06 · НЕЗАВИСИМАЯ ПРОВЕРКА

Доказать качество: baseline → RED → GREEN → REFACTOR

baseline и RED выполняются до первого агента, GREEN и REFACTOR — на границах DAG. Без корректного RED патч не попадает в GREEN.

  • baseline должен пройти на исходном коде — иначе задача или тесты сломаны до начала работы.
  • RED: падают ровно expectedRedTests, и только с ERR_ASSERTION. Ошибка импорта, сети или runner не доказывает RED.
  • GREEN: к снимку применяется вывод implement-узла; целевые, обязательные и регрессионные тесты должны пройти.
  • REFACTOR прямо зависит от GREEN и получает его снимок. Провал GREEN блокирует REFACTOR.
  • verifyArtifact вызывается после сохранения output, но до completed и запуска потомков — поэтому провал останавливает ветку.
  • Success выдаёт только evaluator. stopReason: completed и самоотчёт агента — не оценка корректности.

Артефакт шага

EvaluationResult: success / failed / inconclusive + отчёты фаз, exit codes, хеши тестов

Не путать

Пропуск тестов — не GREEN. Неполное доказательство — inconclusive, а не успех. Изоляция процессная, не OS sandbox.

Где смотреть

tdd-evaluator.md · deepseek-tdd.md

ШАГ 07 · ПАМЯТЬ И ОБУЧЕНИЕ

Сохранить опыт и замкнуть петлю

Попытка становится единицей обучения, а не строчкой в чате.

  • Metrics: spans фаз, usage, расчётная стоимость, coverage flag. Расходы провалов и повторов тоже сохраняются.
  • Attempt record: состояние, проверки, артефакты и метрики. После падения процесса попытка становится interrupted, а не success.
  • Feedback: новая immutable-версия строится только из завершённых train-попыток строго до cutoff.
  • Для held-out/frozen исходы сохраняются, но обучение на них запрещено. Frozen отказывает в обновлении истории.
  • Награда LinUCB считается по измеренному времени и расчётной стоимости подтверждённого success; inconclusive не обучает.
  • Неудачные исходы не удаляются. Обновление Feedback — явный шаг доверенного приложения, а не скрытая запись банка.

Артефакт шага

outcome + revision Feedback + запись попытки в Strategy Bank

Не путать

Польза обучения пока не доказана полной серией. Есть полный перебор одной учебной задачи и повторные проверки; перенос на независимые задачи требует отдельной серии.

Симулятор · учебная модель

Как муравьи собирают расписание

Восемь работ, два слота, три колонии и общий бюджет оценок. Нажимайте «Шаг» и смотрите, как феромоны, UCB, элита, локальный поиск и репликация меняют план. Это не вызов Python-решателя: модель повторяет механику, но не измеряет качество LLM.

Лучшее расписание

итерация 0 / 60
оценок 0 / 60 лучший Cmax — последний муравей — колоний 3

Полосы — окна работ в лучшем найденном расписании. Цвет — тип работы, подпись — длительность. Слоты логические: два «агента» могут работать одновременно. Один шаг = один муравей; в реальном поиске на итерацию приходится несколько муравьёв.

Колонии и UCB

кому дать бюджет
колонияα / βρ / q₀запускинаградаUCBCmax

UCB-бонус = c·√(log T / запуски). Он помогает не застрять на первой удачной колонии. Это выбор колонии, а не стратегии LLM. На каждом шаге UCB выбирает ровно одну колонию.

Феромоны

слабеесильнее·обводка — путь последнего муравья

Строки — позиции в перестановке, столбцы — работы. Испарение и отложение идут только в колонии, выбранной UCB.

Элитный архив

лучшие расписания

Элита усиливает феромоны выбранной колонии. Это не Strategy Bank: архив живёт внутри поиска и не хранит историю LLM-попыток.

Как это читать

механика
  • Муравей на каждой позиции выбирает из готовых работ: τα·ηβ, с вероятностью q₀ — жадно, иначе рулеткой.
  • SSGS ставит работы по порядку на самое раннее допустимое время, соблюдая два слота.
  • UCB выбирает колонию; элита подкрепляет лучший след; LS пробует обмены; при улучшении появляется новая колония.
  • Цель — минимум Cmax: момента завершения последней работы. В реальном joint-поиске качество маршрута идёт первым слагаемым, а время — вторым.

Честно: симулятор перебирает не все возможные расписания и не доказывает оптимум. Кнопка «полный перебор» проверяет все перестановки восьми работ, но SSGS всё равно эвристика декодирования. В настоящем проекте 3 стартовые колонии и до 100 оценок; здесь — 60 оценок, один муравей на шаг и упрощённые параметры, чтобы механика оставалась наглядной и работала в браузере.

Верхний уровень отвечает на вопрос «какой маршрут вообще пробовать». Средний — «какой колонии дать следующий бюджет». Нижний — «в каком порядке ставить работы». Смешивать их — значит не понимать, почему в проекте два разных bandit-алгоритма.

Контекстный LinUCB стратегий пока не является входным вектором UCB колоний: у них разные пространства решений и разные награды.

Strategy Bank ≠ EliteArchiveПостоянная история попыток и временная полка лучших расписаний

Strategy Bank — SQLite-хранилище: версии стратегий, задачи, попытки, события, артефакты по SHA-256. Живёт между задачами и перезапусками.

EliteArchive — ограниченный список лучших расписаний внутри одного запуска solver. Используется для усиления феромонов и инициализации новых колоний, исчезает вместе с поиском.

Поэтому фраза «MetaACO+bank» означает доступ к межзадачной истории. В обоих режимах элитный архив по умолчанию включён — это не одно и то же.

В банке хранятся и провалы, и отмены. «Чистить неудобное» нельзя: это искажает обучение и отчётность.

Прогнозы используются для допуска и планирования. После исполнения они сравниваются с измерениями, но не подменяют их. Верхняя граница стоимости появляется только из quote бюджетного адаптера.

Стоимость успешной попытки без полного покрытия вызовов не выдаётся: лучше null с причиной, чем красивая цифра.

completed ≠ success, а падение ≠ REDУспех — это доказанный исход, а не финальное сообщение агента

stopReason: completed значит, что Harness довёл граф до конца. Это не значит, что код правильный, тесты настоящие, а бюджет не превышен.

RED считается доказанным, только когда на исходном коде падают ровно ожидаемые тесты и только с ERR_ASSERTION. Сбой импорта, недоступная сеть или ошибка runner — это ошибка среды; она даёт inconclusive, а не RED.

GREEN и REFACTOR прогоняют набор заново по закреплённым тестам. Если GREEN упал, REFACTOR блокируется. Итоговый статус выставляет независимый evaluator, а не автор патча.

Лимит бюджета — не то же самое, что quoteРезерв, верхний предел и фактический расход

Лимит (policy.maxCostMicrounits) говорит, сколько всего можно потратить. Quote — гарантированный верхний предел конкретного запроса, включающий input bounds, output/reasoning cap и доп. начисления. Без такого предела вызов отклоняется до сетевого I/O.

Перед dispatch сумма резервируется в SQLite ledger. Параллельные запросы не могут потратить один и тот же остаток. После нормального finish резерв сверяется с тарифом, остаток освобождается; при ошибке или неизвестном usage резерв удерживается.

Это защита от перерасхода, а не доказательство отсутствия скрытых retry внутри провайдерского адаптера. Их нужно отключать или закладывать в quote.

Immutable-версии и provenance: почему всё хешируетсяarmId, snapshot, cutoff и SHA-256 артефактов

Стратегия, решение селектора, снимок истории и артефакт не перезаписываются. Новая версия — это новый объект со ссылкой на предыдущий. Поэтому можно ответить на вопрос «почему система поступила так в тот раз».

armId — SHA-256 от стратегии и маршрута. Смена версии стратегии, модели, инструментов или concurrency создаёт новый arm: старые награды не наследуются.

Cutoff отсекает будущее: в обучающий снимок попадают только попытки, завершённые строго до него. Хеш проверяет целостность, но не удостоверяет автора: локальный банк можно подделать.

DAG: зависимости — не порядок, слоты — не CPUЧто именно гарантирует исполнитель

План v3 задаёт узлы, зависимости, входы и веса слотов. Зависимость без input означает только «начни позже», а не автоматическую передачу результата. Артефакт передаётся, только если он явно указан во inputs.

Готовый узел запускается, если его slots помещаются в свободную ёмкость. Барьеров между независимыми ветками нет: потомок стартует сразу после своего producer. Слоты логические; они не ограничивают CPU или RAM процесса.

completed графа не финализирует попытку. Это делают evaluator, metrics и оркестратор отдельными шагами.

Train, held-out и frozen: где можно учитьсяПочему замороженный снимок важнее «умного» обновления

История делится по задачам и семействам заранее. Награда и обновление обучающей истории строятся только по train-попыткам, завершённым до cutoff. Validation и test не участвуют в выборе.

На отложенном тесте используется один закреплённый frozen-снимок: новые исходы можно сохранять, но нельзя подмешивать в обучение. Иначе сравнение режимов превращается в подгонку.

Даже одинаковый seed не делает ответы реальной LLM побитово воспроизводимыми. Воспроизводится протокол, а не текст модели.

Почему это не «цепочка промптов»Проверяемые границы вместо надежды на модель

Цепочка промптов передаёт текст дальше и верит, что модель сделала правильно. Здесь между шагами стоят проверяемые контракты: схема плана, лимиты, резервы, независимые тесты, артефакты по хешу и явные причины отказа.

Планировщик, исполнитель и оценщик — разные компоненты с разными правами. Модель не решает, прошла ли она тесты, и не выбирает себе бюджет.

При этом промпт-инъекция не исчезает: JSON-envelope не защищает модель от вредоносного текста в артефакте. Права детей задаёт конфигурация профиля.

Что уже доказано, а что только реализованоТри честных статуса этой карты

В коде, проверено офлайн — есть реализация и тесты без реальных LLM. Это не доказывает экономию или качество на живых задачах.

С оговорками — работает, но охват, перенос или серия не завершены: cost coverage, перенос маршрутов, установка в профиль.

Цель — заявлено в архитектуре, но не доказано: польза обучения на независимых задачах, полная серия из семи baseline, воспроизводимый релиз.

Зелёный статус на карте не означает «научно превосходит альтернативы». Он означает «реализовано и проверено на офлайн-тестах».

Реальные эксперименты · 18–19 ноября 2026

От полного перебора к выбору MetaACO

Задача «Резервирование товара» выполнялась на Lenovo через DeepSeek Flash и Pro. Цель — измерить маршруты одной задачи, получить эталон для поиска и проверить выбранные муравьями варианты повторно.

Почему 1 836 маршрутов

Каталог позволяет включать или пропускать анализ, проектирование и ревью, выбирая одну из двух моделей. Обязательный рефакторинг имеет две модели. Реализация выполняется одним агентом либо двумя компонентами, а тестовый план добавляется опционально.

Для монолита существует 2 × (1 + 2 × 2) = 10 сочетаний реализации, тестового плана и интеграции. Для компонентов — 2² × 2 × 3 = 24. Общий размер — 3³ × 2 × (10 + 24) = 1 836: 540 монолитных и 1 296 компонентных вариантов.

Число относится к этому каталогу. Оно не включает все возможные промпты, зависимости и перестановки расписания. В полном переборе порядок маршрутов фиксирован; каждый получает один реальный запуск.

Что происходит в каждой попытке

Одинаковая исходная версия кода → baseline и ожидаемый RED → вызовы моделей по графу → независимый GREEN → рефакторинг → повторные тесты.

Приёмка проверяет успешное резервирование, нехватку остатка, неизвестный SKU, неизменность входных данных и сохранение version(). Модель получает задачу и артефакты родителей. Обязательные тесты закреплены заранее. Навык write-tests в этой серии создаёт короткий тестовый план; набор приёмки он не расширяет.

Тесты исполняются в Docker на Lenovo без сети, с файловой системой только для чтения, непривилегированным пользователем и ресурсными лимитами. Harness и API-клиент работают снаружи контейнера.

SQLite-банк сохраняет все исходы, код, события и отчёты тестов. Время измеряется, стоимость рассчитывается по токенам и закреплённому тарифу. Отчёт обновляется после каждой попытки.

Протокол исправления · Исполняемый перебор

Что выбрали муравьи по накопленному опыту

Настоящий многоколониальный MetaACO выполнил десять поисков с seeds 0–9, по 100 локальных оценок. Маршруты могут посещаться повторно. Для качества использованы 1 716 подтверждённых исходов успеха или провала тестов; длительности прогнозируются по медианам измерений узлов.

Восемь поисков выбрали route-0001, один — route-0011, один — route-0069. Это выбор по полной истории той же учебной задачи. История подана экспериментальному Python-запуску явно; обычный runSkillAttempt исключает собственную задачу из прогноза качества.

Локальная оценка не вызывает DeepSeek и не доказывает прохождение тестов нового исполнения. За ней следует реальная проверка выбранного маршрута.

Открытые проверки — семь baseline при одинаковом числе реальных исполнений, перенос на независимые задачи с замороженной историей, повторяемость результатов и восстановление полноты стоимости первой серии. Эти эксперименты подтверждают исполнение и восстановление хороших маршрутов на одной задаче. Преимущество MetaACO и обобщение опыта ещё требуют измерений.
